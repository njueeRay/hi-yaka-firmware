# 50 文档与飞书同步

## 双端原则

Markdown 是可审计本地工作真值；飞书是团队阅读、协作和附件入口。每一对文档在 `docs/governance/FEISHU_SYNC_REGISTRY.md` 登记本地路径、飞书 URL/token、revision、最后同步时间和差异状态。

## 更新规则

1. 修改前读取本地和飞书现状；
2. 区分事实、需求、假设、建议和未知；
3. 局部修改，不覆盖飞书中仍有价值的历史、图片或评论；
4. 上传的审计附件保留日期/版本，并记录 SHA-256；
5. 回读飞书 revision 和关键章节，确认更新成功；
6. 同步登记写回 Git，并在变更日志中记录影响范围。

产品 PRD 的本地源是 `references/yaka-3.0-prd.md`，飞书副本是 `01 产品与使用 / 01 产品需求与交互状态`。Owner 决策台账的本地源是 `references/yaka-3.0-owner-decisions-and-todos.md`，飞书副本位于 `03 协作、决策与调研`。前者描述产品合同，后者只描述当前决定、角色和需要裁决/提供的事项；不要把两者合并成一份无法阅读的长文档。

硬件主文档只摘要当前有效结论，原理图/PCB/SMT 报告作为版本化附件。若附件与活体 EDA 冲突，标注失效并重新生成审计，禁止静默改写旧附件。

## 缺陷专项与飞书台账

HiYaKa 的一个独立故障对应一份 `docs/bringup/` 下的 Markdown 专项文档和“04 测试与发布 / HiYaKa 反馈与处理台账”的一条“问题”记录。文档按 `docs/governance/ISSUE_ANALYSIS_TEMPLATE.md` 的六节组织：结论、现象、排查分析、解决方法、验证与关闭标准、证据来源；已确认事实、推断和未知分开写。不得把 LCD、NFC、麦克风合成一条台账记录。

飞书“01 测试与发布”是要求、模板和入口；动态状态以多维表格为准。台账的“反馈内容”保留原始现象，不在后续覆盖；“处理意见/最新进展”记录当前结论与专项文档入口；附件字段保存该问题的当前专项 Markdown。每次修改先按问题编号或记录 ID 查询是否已登记，避免重复新建；修订后的附件保留版本或哈希追溯，状态必须随实板证据而不是文档完成而变化。
