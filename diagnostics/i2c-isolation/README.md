# HiYaKa 共享 I²C 隔离诊断

仅用于已拆除 L7、扬声器断开且温度正常的受控样机。构建目标是 ESP32-C6 / ESP-IDF 6.1。诊断保持 GPIO23/PA_EN 为低电平，不启动 LCD、音频、马达、TF 或 NFC；不会向 PN532 发送命令。

程序按 100 kHz → 25 kHz → 25 kHz → 100 kHz 的顺序，分别测 PCA9557 单独读、ES7210 单独读、分开写寄存器地址再读、以及多器件交替访问。每个速率阶段还会对 PCA9557、ES7210、QMI8658A 各执行 128 组“最多五次、立即且静默重试”的读取，分别统计第 1–5 次尝试的结果、在哪一次恢复、以及五次后仍耗尽的次数；这与产品固件的容错路径直接对应。第二版增加四类空闲后首笔对照：三器件的地址 probe、PCA9557 安全写 `0x01=0x40`、QMI 成功读取后立即读 PCA，以及空地址 `0x55` NACK 后立即读 PCA。第三版再增加 I²C bus reset 对照和 0～20 ms 的前置事务衰减曲线，用于判断恢复来自持续的控制器状态修正，还是短时总线活动窗口。多器件交替阶段仍只向 PCA9557 输出锁存反复写安全值 `0x40`，保持马达与功放关闭；读取 PCA9557 `0x01`、ES7210 `0x0B`、QMI8658A `0x00`，并探测 PCA9557 `0x19`、ES7210 `0x41` 与 ES8311 `0x18`。每一项按成功、NACK、未找到、超时及其它错误计数。地址探测的总线速率不纳入 25/100 kHz 定量比较；速率比较以设备句柄上的读写事务为准。该程序运行时 LCD 画面不会刷新，`0x40` 会把背光控制锁存置低，可能使已有画面暂时消失；实验后恢复产品镜像。

这项对照能判断故障是否仍在无显示、无音频任务时发生，是否主要表现为地址应答、单器件寄存器读、多器件交替读写中的哪一种异常，以及降低速率是否明显改善。拆成两笔的读法是**诊断对照**，并非直接推荐修改产品驱动；PCA9557 和 ES7210 数据手册都描述了带重复起始的寄存器读。`ESP_ERR_INVALID_RESPONSE` 只能说明该事务收到 NACK，不能单独定位是地址字节还是数据字节。静态 GPIO 高电平、地址级 ACK 与一次读写成功也不能证明总线波形、A0 电平或芯片焊接合格。

当前 PN532 SET0/SET1 悬空，实验不修改其硬件状态，因此不能排除它对共享总线的干扰；若 A0 测量和软件统计矛盾，需要同步实测 R8 的 A0 侧电压。实验结束应恢复既有横屏诊断镜像并校验。

## 2026-11-27 c0 实板结果

四个速率阶段各完成 128 组五次立即重试：PCA9557 `0x01` 读取第一次尝试 `0/512` 成功、第二次 `512/512` 成功；ES7210 `0x0B` 读取第一次约 `4/512` 成功，其余均在第二次恢复；QMI8658A `0x00` 读取第一次 `512/512` 成功。三者均没有五次耗尽。25 kHz 与 100 kHz 的模式相同，不能把异常归因于 100 kHz 过快。

该结果修正了较早的“PCA9557 特异性首访失败”表述：现象至少覆盖 PCA9557 与 ES7210，但不覆盖同总线 QMI8658A。当前更窄的描述是“空闲后首笔事务与目标/事务形态相关”，而不是“PCA9557 已损坏”或“整个共享 I²C 控制器失效”。本诊断的 PCA 指标是寄存器读；产品菜单 `PCA FIRST` 只统计 PCA9557 寄存器写第一次失败，二者不得直接相加或当作同一故障率。

### 第三版：首访有效窗口

第三版在 c0 上得到以下 64 次重复结果：QMI8658A 成功读取或空地址 `0x55` 的预期 NACK 作为前置事务时，间隔 `0 / 100 / 250 / 500 / 1000 / 2000 / 5000 µs` 后读取 PCA9557 均为 `64/64` 成功；间隔 `10000 / 20000 µs` 后均为 `0/64` 成功，全部地址 NACK。`i2c_master_bus_reset()` 自身 64 次均返回成功，但无论紧接着读取 PCA，还是再等待 10 ms，PCA 都是 `0/64` 成功。

该结果把“任意前置活动有帮助”进一步定量为一个位于 5～10 ms 之间的短时窗口，并否定了“复位 I²C FSM 即可恢复”这一候选。它仍不能单独区分焊盘模拟边沿、共享支路负载、目标器件首帧容差与 ESP32-C6 首帧波形差异；精确物理归因需要在 U3 焊盘处同步捕获 SDA/SCL、A0、RESET# 与 VDD。短周期 keepalive 或受控预事务只能记为已验证的绕过方案，不能写成根因修复。

### 产品负载下的预探测反例

随后在同一 GPIO Fast 菜单负载上测试“每次真实 PCA9557 寄存器写前先探测 PCA 地址”。无预探测基线在 uptime 44 秒累计 `pca_first=979`。10 ms 探测版同一时点为 `pca_preflight=997`、真实写 `pca_first=63`，下降约 93.6%，但没有归零；120 秒窗口末仍为 `pca_preflight=2827`、`pca_first=221`。1 ms 探测版则在 uptime 118 秒达到 `pca_preflight=7916`、`pca_first=7012`，并出现一次 `pca_exhausted`、一次 RASET `refresh_failed`，菜单局刷由基线约 30 ms 恶化到约 100 ms。

因此地址预探测只证明“前置地址活动可暂时改善后续事务”，不构成产品修复。10 ms 版本仍漏出真实写首败。1 ms 版本已由 ESP-IDF 6.1 源码定性：本构建 `CONFIG_FREERTOS_HZ=100`，`pdMS_TO_TICKS(1)` 为 0；`i2c_master_probe()` 最终以零等待时间获取完成信号量并触发软件超时，所以它不是更短的有效总线事务，也不能提供新的板级电气证据。在当前 tick 配置下继续枚举 2／3／4 ms 只会重复零 tick 错误，诊断开关已从当前源码移除。原始日志保留在本地证据目录 `pca-preflight-20261127/`，实验后产品应用重新写回并通过摘要校验，60 秒启动窗口重新进入 GPIO Fast，末值 `pca_first=1354`、`pca_exhausted=0`、`refresh_failed=0`。

本版诊断镜像 SHA-256 为 `BBD0457C2CD9C0843E6A649A86CFC930908FB5D7C917CD184202DBD55F75BBBF`。实验前读取的 c0 启动区 SHA-256 为 `220134295F26E0EB710E4F975A6648AC0BC3E94CCF874024712B329FEDFD5472`；实验结束后该启动区和 GPIO Fast 产品应用均已写回并通过 esptool 写后验证。恢复启动日志再次进入横屏 GPIO Fast 路径，五次整屏约 `803.6～803.7 ms`，55 秒窗口内 `pca_exhausted=0`、`refresh_failed=0`，但 `pca_first` 仍从启动继续增长，说明恢复产品与修复底层异常是两个不同结论。
