# YaKa 3.0 开发协作与文档规范

> 版本：1.0  
> 生效日期：2026-10-29  
> 适用范围：YaKa 3.0 固件、硬件、产品应用、制造资料与飞书协作

## 1. 目的

本规范解决五类常见失控：把历史仓库继续当主线、直接在公开仓库开发、长期不吸收小智上游、把飞书和 Git 维护成两份竞争真值、用“编译通过”替代硬件与产品验证。

## 2. 仓库与远端职责

| 对象 | 地址/位置 | 职责 | 禁止事项 |
|---|---|---|---|
| 私有固件开发仓库 | `njueeRay/hi-yaka-firmware` | 固件开发真值、内部架构/硬件/治理资料、完整 PR/CI 历史 | 不作为公开发布物直接镜像 |
| 公开产品仓库 | `ChatChatTech/yaka` | 对外产品仓库；可发布固件快照到 `/firmware`，应用放其他顶层目录 | 不暴露私有提交历史、内部审计、服务器信息和未批准功能 |
| 小智上游 | `78/xiaozhi-esp32` | 平台能力与基础设施来源 | 不把上游主分支直接当 YaKa 发布分支 |
| 历史仓库 | `ChatChatTech/yaka-firmware` | 只读参考和历史追溯 | 不继续叠加新功能、不作为依赖基线 |

私有仓库推荐远端：

```text
origin   -> njueeRay/hi-yaka-firmware
upstream -> 78/xiaozhi-esp32
public   -> ChatChatTech/yaka（仅用于受控快照发布，不做日常同步）
```

## 3. 分支与变更流

- `main`：随时可构建、可回归；不接受未通过基础检查的直接开发提交；
- `feature/<topic>`：产品功能或驱动开发；
- `fix/<topic>`：缺陷修复；
- `docs/<topic>`：文档与治理；
- `upstream/<tag-or-date>`：仅在需要审阅较大上游升级时使用的临时集成分支；
- 发布使用带注释 tag，例如 `yaka-v3-m1.1`，不得用移动标签覆盖旧版本。

日常开发流程：

1. 从最新 `main` 建短生命周期分支；
2. 把硬件/产品契约写成测试和配置，再实现代码；
3. 本地或 Raynode 完成格式、聚焦测试、ESP-IDF 6.1 构建和产物哈希；
4. 通过 PR 合入私有 `main`；PR 必须声明范围、风险、验证等级和未验证项；
5. 需要发布时，从私有仓库的已验证 SHA 生成干净快照，经过边界扫描后提交到 `ChatChatTech/yaka/firmware`；
6. 在 `firmware/PUBLIC_RELEASE.md` 登记私有来源 SHA、上游基线、SDK、验证等级和公开提交 SHA。

## 4. 小智上游同步

上游同步不是实时镜像，而是有版本、有验证、有退出条件的工程变更。

1. 记录当前上游 tag/SHA 和本地基线；
2. `fetch upstream`，阅读目标区间 release notes、构建系统、分区、音频、协议和板型变化；
3. 在独立集成分支合并或变基；长期产品分支优先采用 merge 保留来源关系，不重写已共享历史；
4. 冲突按三类处理：平台通用能力吸收上游；YaKa 板级事实保留本地；产品行为不得由上游默认值覆盖；
5. 运行 host tests、IDF 6.1 全构建、资源变化比较；有样机后追加 L1/L2 回归；
6. PR 单独合入，不把上游升级和产品新功能混成一个不可审阅变更；
7. 更新 `UPSTREAM.md` 和版本/决策日志。

若上游新版本尚不支持当前 ESP-IDF 6.1 或破坏 YaKa 板级契约，保持已冻结节点，不为了“最新”牺牲可重复构建。

## 5. PR 最低要求

每个 PR 至少包含：

- 目的与非目标；
- 影响模块、硬件 revision、上游和 ESP-IDF 基线；
- 用户可见行为和兼容性变化；
- 风险、回退方式、数据/分区/OTA 影响；
- 已执行命令、测试结果、日志/产物入口；
- 明确证据等级：L0 构建、L1 板级、L2 功能、L3 系统；
- 未验证项和继续推进所需条件；
- 若修改 GPIO、地址、极性、PCA 位定义、音频格式或分区，附接口契约和硬件文档更新。

禁止在一个 PR 中同时进行大规模上游同步、架构重写和产品功能开发。确实无法拆分时，先提交机械同步，再提交 YaKa 适配，最后提交产品行为。

## 6. 提交与版本

- 提交应单一目的、可审阅、可回退；生成物和来源变更分开；
- 推荐前缀：`feat:`、`fix:`、`refactor:`、`test:`、`docs:`、`build:`、`chore:`、`upstream:`；
- 版本必须能反查 Git SHA、ESP-IDF、上游 SHA、硬件 revision、sdkconfig/分区和构建容器；
- 不把个人凭据、服务器地址、私有附件、临时日志和未脱敏串口数据提交到公开仓库。

## 7. 文档分层与所有权

| 文档 | 回答的问题 | 主要事实源 |
|---|---|---|
| 产品 PRD | 为什么做、对用户承诺什么、验收是什么 | 产品评审与批准需求 |
| 硬件研发主文档 | 当前阶段、Gate、材料入口、周进展和阶段结论 | 各专项事实源的索引与裁决 |
| 硬件模块接口契约 | 固件连接到哪里、极性/地址/顺序是什么 | R1.6、活体工程、器件资料 |
| 固件架构 | 如何分层、谁拥有资源、数据怎样流动 | 代码与架构决策 |
| 产品数据与使用手册 | 用户如何使用、看到什么、数据如何处理 | 已批准产品行为和已验证实现 |
| 验证/缺陷/发布 | 什么已被哪一级证据证明 | 原始日志、样机、产物与测试报告 |
| 工作日志 | 本周做了什么、Gate 是否变化、下一步是什么 | 已合并 PR、测试和决策记录 |

文档不得相互复制成长篇竞争真值。主文档负责导航和阶段判断；专项文档负责可执行细节；代码/配置必须引用稳定契约而不是聊天结论。

## 8. 周进展日志规范

工作日志按自然周归类，标题使用 `YYYY.MM.DD–YYYY.MM.DD｜周主题`。同一周内的仓库、代码、文档和发布工作不再拆成多个同日标题。

每周条目至少包含：

1. **硬件/制造线**：版本、审计、打样、物料、样机和 Gate；
2. **固件/应用线**：功能、测试、构建、发布和验证等级；
3. **文档/协作线**：PRD、接口、决策、附件和索引；
4. **本周 Check**：可核验的完成/未完成清单；
5. **阶段结论**：当前 Gate、置信度、阻断项和下一周目标。

历史事实发生变化时，标记由哪个版本/证据取代，不静默删除。工作日志不堆叠细碎操作命令；命令、完整日志和哈希进入测试或发布记录。

## 9. Git 与飞书双端同步

- Git Markdown 是可审计工程事实源；飞书是协作阅读、评论、索引和附件入口；
- 修改前读取两端当前版本；飞书 revision 仅是最近回读记录，不是永久并发锁；
- 已有飞书图片、评论和附件的主文档采用章节级更新，不全文覆盖；
- 附件变化必须以新版本上传，登记 SHA-256、文件 token、适用版本和替代关系；
- 每次写入后回读标题、关键段落和 revision；只收到 API 成功不算同步完成；
- 两端冲突时按证据等级裁决，不能按“谁更新时间晚”自动覆盖；
- 新建文档必须同时进入 00 项目索引、硬件主文档适当位置和本地 `FEISHU_SYNC_REGISTRY.md`。

## 10. 验证与发布边界

- L0：静态检查、host test、编译、链接、镜像/分区检查；
- L1：实板上电、下载、UART、GPIO、I²C、SPI、I²S 等板级证据；
- L2：面向产品功能的可重复验证；
- L3：长稳、功耗、温升、声学、射频、异常恢复、OTA 和整机系统验证。

任何发布说明必须说清最高证据等级和未覆盖项。仿真器的通过属于 L0/L0.5 辅助证据，不能替代 L1 以上的实板证据。

## 11. 公开快照发布检查

发布到 `ChatChatTech/yaka/firmware` 前必须：

- 从已合入、已标记的私有 SHA 生成快照，不复制 `.git`；
- 排除 Agent/Skill、飞书 token/revision、服务器凭据、内部 PRD、未批准审计、采购与个人信息；
- 运行敏感信息和内部路径扫描；
- 在公开树重新运行适用测试和构建；
- 更新 `PUBLIC_RELEASE.md`，注明快照性质、来源基线、验证等级和已知限制；
- 通过公开仓库 PR 或受保护分支规则合入；紧急直推也必须留下等价审计记录。

## 12. 完成定义

一项工作只有同时满足以下条件才算完成：实现已合入；适用层级测试已通过；文档和接口契约已更新；证据可回读；未验证项明确；若涉及公开发布，边界扫描和来源登记已完成。
