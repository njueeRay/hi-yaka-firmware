# HiYaKa 固件 PRD 与里程碑

> 文档性质：固件产品需求、工程边界、里程碑与验收真值  
> 本地真值：本文件  
> 产品输入：HiYaKa 产品 PRD v0.4（当前产品工作基线/待最终产品评审）
> 软件基线：xiaozhi-esp32 v2.5.2 / `49b4380`，ESP-IDF 6.1  
> 日期：2026-11-01

## 1. 北极星目标

让 HiYaKa 在无 PSRAM 的 ESP32-C6 上稳定完成“AI 对话 + 本地录音”双核心，并具有清晰状态、可靠数据、外设降级、用户确认升级和可诊断恢复能力。

## 2. 范围与非目标

范围包括板级启动、显示/输入/反馈、真实音频、TF 录音、Wi-Fi/小智对话、NFC、诊断和 OTA 产品策略。网络协议、Opus、Wi-Fi、LVGL、NVS 和 OTA transport 优先复用小智；HiYaKa 不重新实现已有基础设施。

非目标包括 4G、5 GHz、蓝牙音频、摄像头、触摸、游戏，以及未经专项证明的 C6 设备端全双工 AEC。

## 3. 不可破坏的合同

1. 硬件 pin、地址、极性、电源链、Flash 分区和启动安全态必须可追溯到冻结硬件资料。
2. 产品行为由批准 PRD 决定；驱动对象存在不等于功能可用。
3. 所有跨任务队列有容量、超时、满载策略和指标；音频和 UI 不使用无界缓存。
4. I²S RX 只有一个所有者；对话和录音通过采集适配层分流。
5. OTA 兼容身份包含产品、硬件 revision、分区和最低允许版本；升级不得破坏已提交录音。
6. 任何“通过”必须声明证据等级，L0 构建不得表述为实板通过。

## 4. 功能需求

### YFWR-01 板级启动与健康（P0）

- 输出复位原因、Flash ID/容量、内部堆和固件身份；
- 初始化 GPIO/I²C/PCA9557 安全态，探测五个固定 I²C 地址；
- 每项能力具有 `unavailable/initializing/ready/degraded/failed` 状态和稳定错误码。

**DoD**：IDF 6.1 可复现构建；首板日志证明 Flash、I²C 地址和安全默认态；单个非关键外设失败不造成重启循环。

### YFWR-02 显示、输入与反馈（P0）

- ST7789 200×320 使用局部缓冲，禁止默认双全屏缓冲；
- ADC 键阈值用每台/每批实测分布标定；实体键事件与产品语义分层；
- RGB、五灯链、振动和提示音由统一反馈服务仲裁优先级。

**DoD**：记录 UI 内存、刷新时间、按键分布和反馈冲突矩阵；上电无误亮、误振。

### YFWR-03 音频对话（P0）

- 验证 ES7210 双麦、参考通道 slot，第一上行通道必须是预期麦克风；
- ES8311 稳定后才开启 HT8691R PA，停止时先关 PA；
- C6 第一版使用 LiteAudioEngine 和服务端 AEC/受控打断策略。

**DoD**：通道映射、采样率、底噪、增益、削波、播放功率、爆音和打断均有实板记录。

### YFWR-04 本地录音与 TF 可靠性（P0）

- 录音采用固定块池、有界队列、顺序写入和背压；
- 临时文件、checkpoint、`fsync`、原子完成和启动恢复成套实现；
- 无卡、满卡、坏卡、拔卡和硬切电源均有明确终态。

**DoD**：长录音、随机掉电、容量边界和文件互操作矩阵通过；已提交文件不被半文件覆盖。

### YFWR-05 Wi-Fi 与 AI 对话闭环（P0）

- 复用小智配网、MQTT/WebSocket、Opus 上下行和会话生命周期；
- HiYaKa 只增加产品状态映射、页面反馈、失败恢复和能力门禁。

**DoD**：首次配网、断网重连、服务异常、多轮对话、播放打断和内部堆稳定性通过。

### YFWR-06 NFC、IMU 与辅助能力（P1）

- PN532 首发只读、轮询有超时；IMU 当前轮询，无中断能力；
- 辅助能力失败不阻塞首页、对话或录音。

**DoD**：已批准 NFC 业务完成超时/取消/重复标签测试；IMU 只声明实测能力。

### YFWR-07 电源、电量与受控收尾（P0）

- BAT ADC 只输出经校准的电压/估计档位，不虚构完整充电终态；
- MASTER_SW 硬切电源是正常场景，关键数据写入应缩短脆弱窗口；
- 低电量时禁止高风险 OTA，并给出可理解反馈。

**DoD**：电量曲线、峰值负载、硬切恢复和低电量策略有整机证据。

### YFWR-08 OTA 与恢复（P0）

- 用户确认后升级；录音/文件提交期间不进入 OTA；
- 下载、写入、启动自检、确认和回滚形成闭环；
- 坏包、错误硬件、断网、掉电和启动失败不破坏可用镜像。

**DoD**：故障注入矩阵和回滚证据通过；发布包可追溯到 Git、环境和 SHA-256。

### YFWR-09 诊断与隐私（P0）

- 提供版本、上游 SHA、硬件 revision、复位原因、能力健康、堆/栈/队列和错误码；
- 日志不输出 Wi-Fi 密码、token、完整 NFC payload 或录音内容。

**DoD**：核心失败具有唯一错误码、复现步骤和最小必要持久证据。

## 5. 里程碑

勾选规则：`[x]` 只表示已有对应证据；`[ ]` 表示尚未完成或尚未验证。“代码已写/可以编译”不等于“用户功能已经可用”。

### 5.1 硬件到来前阶段（PH0–PH5）

固件研发同时使用两套阶段，但两者不得互相替代：

- `PH0–PH5` 是硬件到来前可以独立关闭的软件前置阶段，最高只能形成 L0 证据；
- `M1–M7` 是产品固件里程碑，涉及真实外设、声学、功耗、掉电、射频或整机体验的项目必须取得 L1–L3 实板证据。

完成一个 `PH` 阶段时，必须同时完成以下动作后才能改为 `[x]`：

1. 代码、配置、测试或文档达到该阶段完成标准；
2. 保存 Git 提交、测试结果、构建产物或其他 L0 证据；
3. 更新本文件的 checklist、当前进度和下一阶段；
4. 推送 GitHub 私有开发仓库；
5. 同步飞书“01 固件 PRD 与里程碑”，回读 revision，并更新 `FEISHU_SYNC_REGISTRY.md`。

关闭 `PH` 阶段不代表对应硬件功能已经通过。例如 `PH2` 完成只说明状态机和模拟接口可测试，不能勾选 M2 的屏幕、按键或反馈实板验收。

## 6. 当前进度与下一步

### 6.1 已经完成

- 新固件仓库、固定上游、ESP-IDF 6.1 和 `aliyun_raynode` 构建环境已经建立；
- ESP32-C6、16 MiB Flash、DIO、无 PSRAM 等关键构建约束已经固化；
- 启动诊断、I²C 探测和 PCA9557 安全态已经实现并通过软件级检查；
- M2–M5 的真实板级适配已形成 L0 实现：LCD/PARLIO、输入/电池 ADC、RGB/灯阵/马达、ES7210/ES8311、TF/FatFs、本地录音分流与产品运行时均可由分模块开关隔离；
- PN532 与 QMI8658A 已从地址探测升级为完整的 L0 业务驱动；数字音频可在功放禁用时通过 TF 上的 WAV 留样离线核验；
- `hi-yaka` 保持 M1 安全默认态，`hi-yaka-lab` 用于 CI 编译全部适配；两者都不产生实板通过结论；
- 固件 PRD、总体架构、硬件接口契约、协作规范和证据规则已经建立；
- 私有开发仓库与公开 `/firmware` 快照的发布边界已经明确。
- 硬件到来前的 PH0–PH5 已关闭；PH2 建立产品协调者和端口合同，PH3 建立可配置输入、对话恢复、可靠录音、故障注入和页面流程模拟，PH4 建立双 OTA、升级保障、资源预算、故障注入和候选产物追溯，PH5 建立首板手册、15 个模块证据模板、M1–M7 证据映射和不可覆盖记录工具；上述结论均为 L0，不替代 M1 的首板证据。
- 2026-11-04 受控实板测试已确认：固件持续运行，RGB、短振动、部分实体输入、TF 基础写入和 IMU 动态读数取得实板证据。各项仍按对应里程碑完整标准逐项关闭，不因单次运行一并勾选。

### 6.2 尚未完成

- 两块真实样机已在 U11/BOOST 支路复现快速异常发热；根因证据保持 `FAIL`，不得覆盖；
- 当前开发样机已拆除 L7，随后不再快速升温，M1 从“完全阻断”转为“受控复测”；GPIO23 复位弱上拉、下一版 L7/CTRL 设计和功放播放仍未关闭；
- 屏幕完全无背光；PCA9557 IO0 是开漏，当前 `LCD_BL` 没有上拉却有 R86 下拉，实际 Q10 栅极约 0 V。这是已定位的背光硬件设计遗漏；LCD 控制器没有返回数据线，待背光返修后再验证画面；
- 麦克风在 TDM、双麦标准 I²S 单声道以及双声道三种实板配置下，原始接收数据均全零；只选错声道不是唯一原因，需检查时钟、SDOUT1/R65、模拟供电和麦克风偏置；
- PN532 始终未在 `0x24` 应答。PVDD 与 DVDD 同接 `VREF`；C108 实测约 3 V，不能再将“不供电”或该接法直接当成 NACK 根因，待复位、晶振与总线端点核查；
- M2–M6 因上述缺口及可靠性/体验测试仍未完整关闭，M7 未开始；
- 产品侧仍需冻结按键动作、录音规格、NFC 首发业务、离线能力、UI 信息架构和量化体验指标。

### 6.3 下一步开发顺序

1. 保持当前样机 L7 已拆、扬声器断开、PA 软件硬禁用；操作者不在场时保持 MASTER OFF；
2. 按[专项诊断](../bringup/2026-11-04-lcd-nfc-mic-investigation.md)核查背光控制、PN532 复位/晶振/总线和麦克风时钟/数据/偏置，逐项修复并建立新的证据 run；
3. 复测 M1 的电源、Flash、I²C 和安全态；PN532 缺失必须保留为 FAIL，不能因其不阻塞主循环而将“五器件探测”勾选；
4. 屏幕恢复背光后验证全屏色块、方向与页面；麦克风恢复非零数据后验证双麦/参考通道及 TF 录音；扬声器功放必须等 L7 与 CTRL 闭环后单独恢复；
5. 复测 NFC/IMU、配网、弱网、对话、录音并发和掉电恢复；最后收敛 M6/M7 的产品决策和发布证据。

当前结论：**PH0–PH5 的软件 L0 仍有效；当前样机拆 L7 后可受控验证非功放功能，但屏幕、NFC、麦克风明确未通过。`HIYAKA-HW-INC-001` 的 U11/BOOST 风险未关闭，PN532 NACK 根因仍待确定。不得发布或恢复功放。**详见[专项诊断](../bringup/2026-11-04-lcd-nfc-mic-investigation.md)。

详细工程证据见 [M1 基线](../yaka/m1-baseline.md)、[首板验证与证据包](../bringup/README.md)、[硬件连接与固件接口表](../hardware/HARDWARE_MODULE_INTERFACES.md) 和 [固件总体架构](../yaka/firmware-architecture.md)。
